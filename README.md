# CivicGuard PWA

Sistema de Gestión de Emergencias e Incidencias en Infraestructura Urbana — Proyecto Integrador 2 (Ingeniería en Desarrollo y Gestión de Software).

PWA _offline-first_ para reportar incidencias con ubicación GPS y foto de evidencia, incluso sin conexión; los reportes se sincronizan solos al volver la red y los cambios de estatus llegan como notificación push.

## Entorno con Docker

Requiere Docker con Compose v2. Primer arranque: `cp .env.example .env` (ajusta `DB_PASSWORD`) y `docker compose up --build`.

| Servicio    | Puerto del host              | Qué hace                                                         |
| ----------- | ---------------------------- | ---------------------------------------------------------------- |
| `db`        | `127.0.0.1:5432` (`DB_PORT`) | PostgreSQL 16 con volumen `pgdata` y healthcheck                 |
| `liquibase` | —                            | Aplica `db/changelog/` y termina; si falla, `backend` no arranca |
| `backend`   | `3000`                       | API NestJS (`api/`, target `dev`)                                |
| `frontend`  | `5173`                       | PWA con Vite (`web/`, target `dev`)                              |

- **Orden de arranque:** `db` (healthy) → `liquibase` (terminó con éxito) → `backend` → `frontend`. Si `liquibase` falla: `docker compose logs liquibase`.
- **Reinicio limpio:** `docker compose down -v && docker compose up --build` (borra la BD local).
- **Imágenes de producción:** `docker build --target prod ./api` y `docker build --target prod ./web` (Nginx en el puerto 8080, con gzip, `no-cache` para `sw.js`, `sync.js` e `index.html` y `max-age` largo para el resto).

## PWA (React + Vite)

Proyecto en `web/` (React 18, TypeScript, Vite y React Router). Con el entorno de Docker arriba: `http://localhost:5173` (recarga en caliente al editar `web/`).

- **Cascarón estático (RF-1):** `web/index.html` trae encabezado, navegación y _skeletons_ como HTML y CSS propios (`web/src/shell.css`), así que se ven antes de que cargue JavaScript. React solo reemplaza el contenido de `#root`.
- **Rutas lazy:** `/` (Nuevo reporte), `/reportes` (Mis reportes), `/reportes/:id` (Detalle) y `/panel` (Panel). Cada página en `web/src/pages/` es un _chunk_ aparte (`React.lazy` en `web/src/app/App.tsx`); para una página nueva, copia ese patrón.
- **Manifest e instalación (RF-2):** `web/public/manifest.json`, enlazado desde `index.html`, declara los íconos de 192×192 y 512×512 en `any` y `maskable` (`web/public/icons/`) y los colores del splash. Los PNG los dibuja `node web/scripts/generate-icons.mjs` (sin dependencias; se versionan, no se generan en el build): el _maskable_ ocupa todo el lienzo y su escudo queda dentro del 80 % central. `InstallButton` (`web/src/app/InstallButton.tsx`) captura `beforeinstallprompt`, muestra «Instalar CivicGuard» y lo abre al tocarlo; desaparece tras usarlo o con `appinstalled`. En iOS y Firefox no existe ese evento, así que no se muestra nada.
- **Service Worker (RF-3, RF-7):** `web/public/sw.js`, escrito a mano, scope `/`. `install` precachea `PRECACHE` en `civicguard-shell-v<VERSION>` (todo o nada), `activate` borra las demás cachés `civicguard-shell-v*` y reclama clientes, y `fetch` responde los GET desde esa caché primero, salvo las **lecturas de la API** (`GET /api/*` de cualquier origen, sin `/api/health` ni `/api/docs` ni peticiones con `Authorization`), que usan **Network-First con tiempo máximo de 3 s** y respaldo en `civicguard-api-v1` (nombre fijo: sobrevive a los builds; con red se entrega y guarda la respuesta `200`; sin red, a los 3 s o con `5xx` se entrega la copia con la cabecera `X-Served-From: cache`, o un `503` en JSON si no hay copia; un `POST` nunca se intercepta ni se guarda; resultados de los tres escenarios en `docs/mapeo-ciclo-de-vida-sw.md` §5.5), y las imágenes y fuentes estáticas del mismo origen (fuera de `/api/*`), que usan Stale-While-Revalidate (copia guardada al instante y revalidada en segundo plano con `cache: 'no-cache'`, guardando solo respuestas 200 en la misma caché versionada); una navegación sin red abre el cascarón precacheado (`/`), para que la SPA resuelva la ruta y «Mis reportes» y «Detalle» lean IndexedDB (`web/public/offline.html` queda solo si el cascarón no está), y lo que no es GET ni se intercepta. Un SW nuevo **espera**: solo llama a `self.skipWaiting()` al recibir `{type:'SKIP_WAITING'}`, que envía `UpdateNotice` (`web/src/app/UpdateNotice.tsx`, también registra el SW) al pulsar «Nueva versión disponible · Actualizar». `VERSION` y `PRECACHE` de `public/sw.js` son valores de partida para desarrollo: `npm run build` (`tsc && vite build && node scripts/inject-sw.mjs`, también dentro de la imagen `prod`) ejecuta `web/scripts/inject-sw.mjs`, que recorre `dist/`, calcula un hash global (ruta + contenido de cada archivo, sin contar `sw.js`) y reescribe en `dist/sw.js` esas dos líneas: la caché pasa a `civicguard-shell-v<hash de 12 caracteres>` y el precaché lista `/` y todos los archivos de `dist/` (assets con hash incluidos). Un build con otro contenido da otro nombre, y el SW nuevo borra la caché anterior en `activate`. El script sale con código 1 y un mensaje si falta `dist/`, `dist/sw.js` o alguna de las dos líneas.
- **Persistencia local (RF-5):** `web/src/db/idb.ts` abre la base `civicguard` con `idb` (`openCivicGuardDB`) y define los stores `incidents`, `outbox` y `meta`. Cambiar stores o índices exige subir `DB_VERSION` y añadir su paso en `upgrade`. `getDeviceId(db)` devuelve el UUID anónimo del dispositivo (lo crea la primera vez y lo reutiliza). Las operaciones locales son funciones asíncronas sobre esa conexión: `saveIncident`/`getIncident`/`listIncidents`/`deleteIncident` (la foto viaja como `Blob` dentro del reporte y vuelve con su tipo y tamaño), `saveOutboxEntry`/`getOutboxEntry`/`listOutbox`/`deleteOutboxEntry` y `setMeta`/`getMeta`/`deleteMeta`; las de guardado crean o actualizan según exista la clave. Nada de `localStorage`/`sessionStorage`: ESLint lo rechaza.
- **Ubicación (RF-4):** en «Nuevo reporte», el botón «Usar mi ubicación» llama a `useGeolocation` (`web/src/hooks/`), que usa `getPosition` de `web/src/modules/geo.ts`: una sola lectura con `getCurrentPosition` (`enableHighAccuracy: true`, `timeout` de 10 s) que devuelve `lat`, `lng` y `accuracy`. No se pide al cargar la app ni hay `watchPosition` (sin rastreo continuo). Si se deniega el permiso, se agotan los 10 s, el dispositivo no puede ubicarse o el navegador no ofrece la API, se muestra el motivo y `ManualLocationForm` para escribir latitud (−90 a 90) y longitud (−180 a 180; acepta coma decimal); el resultado manual (sin `accuracy`) queda en el mismo estado que el del GPS.
- **Presupuesto de JS inicial (R14):** `npm run check:bundle` (`web/scripts/check-bundle-size.mjs --lazy Panel,camera`, lo corre el job `lint-and-test` tras el build) suma el tamaño gzip de los scripts que carga `dist/index.html` (`<script src>` y `modulepreload`; los chunks de cada página con `React.lazy` no cuentan), imprime cada uno y el total, y sale con código 1 si pasa de 150 KB (1 KB = 1000 bytes). También imprime el tamaño de cada chunk bajo demanda y, con `--lazy`, falla si el panel o la cámara (`import()` dinámico en `useCamera`) dejan de ser chunks propios. Análisis completo, cabeceras de Nginx (gzip, `no-cache` en `sw.js`/`sync.js`/`index.html`) y mediciones de Lighthouse en [`docs/analisis-rendimiento.md`](docs/analisis-rendimiento.md). También falla si `index.html` no carga ningún script o referencia uno que no existe, para no dar por bueno un total de 0.
- **Comandos** (`cd web && npm ci`): `npm run dev`, `npm run build` (comprueba tipos y genera `dist/`), `npm run check:bundle` (necesita el `dist/` del build) y `npm test` (Vitest + Testing Library).
- **Captura de un reporte (RF-4, HU-02/03/04):** «Nuevo reporte» (`web/src/pages/NuevoReporte.tsx`) pide tipo, severidad (`web/src/modules/incident-options.ts`, los valores de los ENUM de la API), descripción (máx. 500, con contador), ubicación y foto, cada campo con su etiqueta y su mensaje de error visible (el foco va al primer campo inválido). Al guardar, `compressImage` (`web/src/modules/image.ts`) reduce la foto en un canvas a 1280 px de lado mayor sin ampliarla nunca y la exporta como JPEG calidad 0.7 (RNF R4); `saveReport` (`web/src/db/idb.ts`) guarda en **una sola transacción** el reporte (con `id` UUID v4 y `createdAt` de la hora de guardado) y su entrada `pending` en el outbox, sin necesitar red. Tras guardar se confirma y el formulario queda limpio. Si falla la compresión o IndexedDB (poco espacio, o navegación privada de Safari, que no admite `Blob` en IndexedDB) se avisa y se conserva lo escrito. El envío al servidor es de la historia SCRUM-177.
- **Envío automático de los reportes (RF-6, SCRUM-177):** `web/public/sync.js` es la **única** implementación del envío; `sw.js` la carga con `importScripts('/sync.js')` y sirve igual con `no-cache` (Nginx y Vercel, como `sw.js`). Toma de IndexedDB las entradas `pending` del outbox (del reporte más antiguo al más reciente) y manda cada una como `multipart/form-data` a `POST <VITE_API_URL>/api/incidents`; la API es idempotente, así que reenviar un `id` ya recibido responde `201` y no duplica. Según la respuesta, la entrada pasa a `sent` (2xx), a `error` (4xx salvo 408/429: reenviarlo fallaría siempre; no atasca a los demás) o queda `pending` (5xx, 408, 429 o sin red), y en ese caso el vaciado rechaza para que el navegador reintente el `sync` con su espera creciente. Un vaciado en curso se comparte (dos eventos seguidos no envían dos veces) y avisa a las pestañas con `{type:'OUTBOX_CHANGED'}`. El SW nunca crea la base de IndexedDB (la crea la app) y necesita `deviceId` y `apiUrl`, que la app deja en el store `meta`: `requestSync` (`web/src/modules/sync.ts`) escribe `apiUrl` (el SW no ve las variables de Vite) y registra la etiqueta `sync-incidents` con Background Sync (Chromium; si el permiso está denegado o no existe, manda `{type:'FLUSH_OUTBOX'}` al SW). `useSyncTriggers` (`web/src/hooks/`) lo pide también al abrir la app, al volver la red (`online`) y al volver la pestaña a primer plano: es el único disparador en Safari y Firefox. Sin `VITE_API_URL` en el build no hay envío y los reportes quedan `pending`.
- **Mis reportes y Detalle (HU-06, SCRUM-181):** `web/src/pages/MisReportes.tsx` lista los reportes con `useOutbox` (`web/src/hooks/`), que lee primero IndexedDB (sin red) y después pide al servidor `GET /api/incidents?reporter_id=<deviceId>` (Network-First del SW) para unirlos con `mergeReports` (`web/src/modules/reports.ts`): lo local conserva su estado de envío y su foto, el servidor aporta el estatus y los reportes que este dispositivo no tiene (entran como enviados). Cada reporte lleva un badge `SyncBadge` con ícono **y** texto (Pendiente, Enviado, Con error; colores con contraste AA) y es un enlace de 44 px a `/reportes/:id`. La lista se refresca sola, sin recargar, cuando el SW avisa `OUTBOX_CHANGED` (un reporte pasó a `sent`) o vuelve la red; si el servidor respondió con la copia guardada (`X-Served-From: cache`) avisa «se muestran los datos guardados». `Detalle` lee de IndexedDB (foto, tipo, severidad, descripción, ubicación, fecha, estado de envío y estatus); el estatus que dijo el servidor se guarda en el propio reporte local (`setServerStatuses`) para verlo sin red; si el dispositivo no tiene el id, lo pide al servidor. Sin red, cualquier navegación abre el cascarón precacheado y la SPA resuelve la ruta. Al abrir un reporte de este dispositivo, `Detalle` pide al servidor el estatus vigente (el que dejó el coordinador, p. ej. al llegar desde un aviso push) y lo guarda; sin red, o si el SW responde con una copia vieja de su respaldo (`X-Served-From: cache`), conserva el último estatus conocido.
- **Avisos de cambio de estatus (HU-07, RF-8, SCRUM-203):** «Mis reportes» muestra `PushButton` (`web/src/components/`, estado en `hooks/usePush.ts`). **Nunca pide nada al cargar**: solo ofrece «Activar avisos»; al tocarlo, `enablePush` (`web/src/modules/push.ts`) pide el permiso de notificaciones **lo primero dentro del clic** (Safari lo exige), lee la clave pública de `GET /api/push/vapid-public-key`, suscribe con `pushManager.subscribe({userVisibleOnly: true, applicationServerKey})` (reutiliza la suscripción que el navegador ya tenga) y manda `{reporter_id, endpoint, p256dh, auth}` a `POST /api/push/subscribe` con el UUID del dispositivo (`getDeviceId`). Si el usuario niega el permiso, la app lo dice y todo lo demás sigue igual; si la API no tiene VAPID (503) avisa que no hay avisos por ahora. Sin soporte (falta `PushManager` o `Notification`: iOS anterior a 16.4 o la app sin añadir a la pantalla de inicio, R3) el botón **no se muestra** y un texto explica que no habrá avisos, sin errores en consola. En `web/public/sw.js`, el evento `push` muestra **siempre** una notificación nativa (`userVisibleOnly`) con el título, el texto y el reporte (`tag` = id del reporte, así un aviso nuevo reemplaza al anterior del mismo reporte; sin datos o con un cuerpo que no es JSON muestra un aviso genérico) y `notificationclick` la cierra y enfoca la app abierta llevándola a `/reportes/:id` (o abre una ventana nueva); solo navega a rutas del propio origen, cualquier otra cosa abre `/reportes`. Para probar en local necesitas HTTPS (el túnel ngrok) y las variables `VAPID_*` de la API.
- **Panel del coordinador (HU-09, RF-9, SCRUM-205):** `/panel` (`web/src/pages/Panel.tsx`, chunk propio con `React.lazy`) **sin sesión solo muestra el login** (`LoginForm`): no pide ni pinta ningún reporte. Entra con `POST /api/auth/login` (`web/src/modules/admin.ts`) y **el JWT vive solo en el estado de React**: recargar o cerrar la página lo pierde, y nada se escribe en `localStorage`, `sessionStorage`, cookies ni IndexedDB. Cualquier `401` (token vencido o inválido, en la lista o al cambiar el estatus) vuelve al login con «Tu sesión venció»; `429`, `503` y la falta de red tienen su mensaje en español (el panel **necesita internet**: sin red lo dice y ofrece «Reintentar»). Las peticiones con `Authorization` no pasan por la caché del Service Worker (`sw.js` las excluye de Network-First: los datos del coordinador no se guardan en el navegador). La lista pide `GET /api/admin/incidents[?status=]` y se filtra por Recibido, En revisión, En atención y Resuelto. El detalle muestra la foto (`photo_url`), los datos, un **mapa estático** (`StaticMap`: mosaico de 3×3 teselas de OpenStreetMap a zoom 16 calculado en `web/src/modules/map.ts`, sin biblioteca ni clave, con su atribución) y el control para cambiar el estatus: elegir el nuevo, «Cambiar estatus» y **Confirmar** (o Cancelar) ejecutan `PATCH /api/admin/incidents/:id/status`; al volver a la lista se vuelve a pedir, así que refleja el estatus nuevo y respeta el filtro. El cambio dispara el aviso push a los dispositivos del reportante (SCRUM-204). Para crear al coordinador, ver «API» → «Coordinador inicial».
- **Sin caché y con túnel:** en desarrollo Vite responde `Cache-Control: no-store`. Para probar cámara, GPS y Service Worker en un teléfono real, define `NGROK_DOMAIN` en `.env` (se añade a `server.allowedHosts` y al CORS de la API) y ejecuta `ngrok http 5173`. Pasos, puertos y validación de contexto seguro en [`docs/reporte-configuracion-entorno.md`](docs/reporte-configuracion-entorno.md).

### Service Worker: cómo funciona y cómo depurarlo

Detalle completo, con el código de cada listener, en [`docs/mapeo-ciclo-de-vida-sw.md`](docs/mapeo-ciclo-de-vida-sw.md). En corto, el ciclo de una versión nueva es `installing` → `installed` (_waiting_) → `activating` → `activated`, y **solo pasa de _waiting_ a `activating` cuando la app envía `{type:'SKIP_WAITING'}`** (el botón «Actualizar»); nada más llama a `skipWaiting()`. Si algo no se comporta como esperas:

1. **Prueba con un build, no con `npm run dev`:** `cd web && npm run build && npm run preview` (`http://localhost:4173`). El hash de la caché y el precaché solo existen tras `npm run build`; con `npm run dev` el SW usa los valores de partida (`VERSION = '1'`).
2. **Mira el estado:** DevTools → **Application → Service Workers**. Ahí ves el worker activo (_activated and is running_), el que espera (_waiting to activate_) y los botones **Update**, **skipWaiting** y **Unregister**. Una versión nueva que no se activa **es lo normal**: está esperando el clic en «Actualizar».
3. **Mira las cachés:** **Application → Cache Storage**. Debe haber una sola `civicguard-shell-v<hash>` tras activarse; dos significa que hay una versión esperando.
4. **Empezar de cero:** **Application → Storage → Clear site data** (o **Unregister** y recargar).
5. **Depura el propio `sw.js`:** su consola y depurador son distintos de los de la página; ábrelos desde Application → Service Workers o, con un teléfono por USB, desde `chrome://inspect/#service-workers`.
6. **Casilla _Update on reload_:** instala y activa el SW en cada recarga. Sirve para **desarrollar** `sw.js`; **desmárcala** para probar el ciclo de vida, porque se salta justo la fase _waiting_.
7. **Sin red:** para comprobar el arranque sin red (el cascarón, y `offline.html` solo si el cascarón falta), marca **Offline** en Application → Service Workers; para una prueba más fiel, apaga el servidor (así se hizo en la evidencia del documento) o usa Modo Avión en el teléfono.
8. **Si `npm run build` falla en `inject-sw`:** `web/public/sw.js` debe conservar `const VERSION = ...;` y `const PRECACHE = ...;` cada una en una sola línea.

### Pruebas E2E: Modo Avión (Playwright)

Paquete `e2e/` (`@playwright/test` 1.64.1, solo Chromium con el perfil de un Pixel 7). `tests/modo-avion.spec.ts` recorre, en un mismo perfil persistente del navegador: primera visita con red (se instala el SW) → **Modo Avión** (se apagan de verdad el servidor de la PWA y el de la API, como en el teléfono) → la app arranca con el cascarón precacheado → captura un reporte con ubicación y cámara simuladas (`geolocation` del contexto y `--use-fake-device-for-media-stream`) → «Mis reportes» lo muestra **Pendiente** y nada llegó al servidor → vuelve la red (se encienden los servidores y la ventana recibe `online`) → el reporte llega con su foto JPEG y pasa a **Enviado** → se fuerza un reenvío del mismo reporte y el servidor lo recibe dos veces pero conserva **una sola fila**. `tests/push.spec.ts` cubre los avisos: cargar `/reportes` no pide permiso ni suscribe → «Activar avisos» pide el permiso, lee la clave VAPID y envía la suscripción con el UUID del dispositivo → llega un `push` al Service Worker (mismo cuerpo que arma la API) y aparece la notificación nativa con el reporte y su estatus → tocarla abre `/reportes/:id` y la cierra. Chromium sin ventana no tiene servicio de push (`subscribe` falla con «push service not available»), así que la suscripción y la entrega del `push` al SW (`ServiceWorker.deliverPushMessage`) se simulan, y el toque se simula entregando el evento `notificationclick`; el permiso exige `channel: 'chromium'` porque el _headless shell_ siempre reporta `denied`. `tests/panel.spec.ts` recorre el panel: sin sesión solo el login y ningún rastro del token en el navegador → filtro por estatus → detalle con foto y 9 teselas de mapa → cambio de estatus con confirmación y lista actualizada → sin red, mensaje claro y recuperación con «Reintentar» (las teselas de OpenStreetMap se responden dentro de la prueba para no depender de internet).

- **Comando:** `cd e2e && npm ci && npx playwright install --with-deps chromium && npm test`. El setup global construye `web/` con la API de prueba (`http://localhost:4181`) incrustada, así que los puertos `4180` y `4181` deben estar libres. El informe HTML queda en `e2e/playwright-report` (`npm run report` lo abre).
- **Sin instalar dependencias del navegador (Docker):** `docker run --rm --ipc=host --user "$(id -u):$(id -g)" -e HOME=/tmp -v "$PWD":/work -w /work mcr.microsoft.com/playwright:v1.64.1-noble npm test --prefix e2e` (requiere `npm ci --prefix e2e` y `npm ci --prefix web` antes en el repositorio).
- **Evidencia:** con `E2E_EVIDENCE=1` las capturas se guardan en `docs/evidencia/e2e-*.png` (sin la variable solo van al informe HTML).
- **Ensayo de la demo (SCRUM-210):** `tests/ensayo-demo.spec.ts` recorre en una sola corrida Modo Avión → sincronización → cambio de estatus en `/panel` → push → detalle (con los dobles de la API y del servicio de push); es el recorrido de [`docs/guia-demo-y-code-freeze.md`](docs/guia-demo-y-code-freeze.md) y no sustituye el ensayo sobre producción.
- **Accesibilidad (SCRUM-206):** `tests/accesibilidad.spec.ts` audita 16 vistas y estados del operador y del panel con axe (WCAG 2.x A/AA y mejores prácticas, incluido el contraste), mide que todo control visible tenga al menos 44 × 44 px y recorre cada vista con `Tab` comprobando que cada control enfocado muestra un indicador. Informe, método y control negativo en [`docs/auditoria-accesibilidad.md`](docs/auditoria-accesibilidad.md).
- **Lighthouse 11 (R1):** `node scripts/lighthouse.mjs <url> --label <nombre> [--categories accessibility,performance,pwa] [--throttling mobile|slow3g]` (en `e2e/`, con el Chromium de Playwright: úsalo dentro del contenedor de arriba con `--network host`) corre `lighthouse@11` en perfil móvil sobre `/`, `/reportes` y `/panel`, guarda una captura del informe y un resumen con puntajes, métricas y versión en `docs/evidencia/lighthouse/<nombre>.json`. `mobile` es el perfil por defecto de Lighthouse (CPU 4×, 150 ms de RTT, 1.6 Mbps: el «Fast 3G» de DevTools); `slow3g` usa 400 ms y 400 Kbps.
- **Alcance:** la API es un doble en el proceso de prueba (`tests/support/fake-api.ts`, mismo contrato multipart); la idempotencia real con PostgreSQL la cubren las pruebas de `api/`. No corre en CI (necesita el navegador) ni cubre WebKit ni un teléfono real.

## Base de datos y migraciones

Liquibase es el único dueño del esquema (el backend nunca crea ni altera tablas). El changelog vive en `db/changelog/`: `db.changelog-root.yaml` hace `includeAll` de `migrations/`, donde cada changeset es un `.sql` con formato Liquibase (`--liquibase formatted sql`), numerado (`0001-…`) y con su `--rollback`.

- **Aplicar:** `docker compose up db liquibase` (el servicio `liquibase` aplica los changesets y termina).
- **Cambiar el esquema:** crea un changeset nuevo con el siguiente número en el mismo PR que el código que lo usa. Nunca edites uno ya aplicado: rompe su checksum y el job `liquibase-validate` del CI falla. Si te pasa en local, recrea la BD con `docker compose down -v`.
- **Revertir el último changeset:** `docker compose run --rm liquibase rollback-count --count=1`.

## API (NestJS)

Proyecto ESM en `api/` (NestJS 12, TypeORM, PostgreSQL). Con el entorno de Docker arriba: `GET http://localhost:3000/api/health` y Swagger en `http://localhost:3000/api/docs`.

- **`GET /api/health`:** `200 {"status":"ok","database":"up"}`; si la BD no responde, `503 {"status":"error","database":"down"}` (el motivo solo va al log).
- **Incidentes** (`api/src/incidents/`, campos en snake_case como las columnas): `POST /api/incidents` acepta `multipart/form-data` (o JSON) con el reporte (`id` UUID v4, `reporter_id` UUID, `type`, `severity`, `description` ≤ 500, `lat`, `lng`; opcionales `accuracy` y `created_at`) y, opcional, un archivo `photo` (JPEG, PNG o WebP, máx. 5 MB); lo guarda con estatus `recibido` y responde `201`. **Es idempotente:** reenviar un `id` ya guardado no crea otra fila y también responde `201` con el reporte original (`INSERT … ON CONFLICT DO NOTHING`). `created_at` es la hora de captura del cliente y `synced_at` la de recepción del servidor. La foto se valida por sus bytes (no por el `Content-Type`), se sube a Supabase Storage con el `id` como nombre y la tabla guarda solo `photo_url`. Errores: campo inválido o no declarado `400` nombrando el campo, foto que no es imagen `400`, foto de más de 5 MB `413`, almacenamiento sin configurar `503` o caído `502` (en ambos no se crea el reporte). `GET /api/incidents?reporter_id=<uuid>` lista los reportes de ese dispositivo, del más reciente al más antiguo; `GET /api/incidents/:id` devuelve el detalle y `404` si no existe.
- **Variables** (las inyecta `docker-compose.yml`): `DB_HOST`, `DB_NAME`, `DB_USER`, `DB_PASSWORD` (obligatorias, sin valores por defecto: la API no arranca sin ellas), `DB_PORT` (5432), `PORT` (3000) y `CORS_ORIGINS` (lista separada por comas; vacía = ningún origen cruzado). Compose la fija a `http://localhost:5173` y, si defines `NGROK_DOMAIN`, a su dominio. Para las fotos: `SUPABASE_URL` y `SUPABASE_SERVICE_KEY` (van juntas o ninguna; la clave de servicio es secreta, solo en `.env` o en el panel de Render) y `SUPABASE_BUCKET` (`incident-photos`, debe ser un bucket **público**). En Supabase: _Storage → New bucket → Public_.
- **Autenticación y administración** (`api/src/auth/`, `api/src/admin/`): `POST /api/auth/login` (`{email, password}`) devuelve `{access_token}`, un JWT HS256 de 8 h firmado con `JWT_SECRET`; las contraseñas se guardan con bcrypt (costo 10) y un correo inexistente y una contraseña incorrecta dan el mismo `401`. El login admite 5 intentos por minuto y por IP (`429` al excederlos; en Render `TRUST_PROXY=1` hace que la IP sea la del cliente y no la del proxy) y responde `503` si falta `JWT_SECRET`. `GET /api/admin/incidents[?status=<estatus>]` lista todos los reportes (más reciente primero) y `PATCH /api/admin/incidents/:id/status` (`{status}`) cambia el estatus (`404` si no existe); ambos exigen `Authorization: Bearer <token>` (`401` sin él, con uno inválido o vencido) y validan el estatus contra el enum (`400`). El guard JWT va en la clase `AdminController`, así que todo endpoint nuevo de `admin` nace protegido.
- **Coordinador inicial:** no hay contraseñas en el repositorio. Con la base migrada: `COORDINATOR_EMAIL=… COORDINATOR_PASSWORD=… npm run build --prefix api && npm run seed:coordinator --prefix api` (mín. 12 caracteres; las variables `DB_*` o `DATABASE_URL` apuntan a la base y, desde fuera de la red de Render, `DB_SSL=true`). Solo guarda el hash y, si el correo ya existe, no lo modifica.
- **Notificaciones push** (`api/src/push/`, RF-8): Web Push con `web-push` y VAPID. `GET /api/push/vapid-public-key` entrega `{public_key}` (la clave con la que el navegador se suscribe) y `POST /api/push/subscribe` (`{reporter_id, endpoint, p256dh, auth}`, los campos de `PushSubscription.toJSON()` más el UUID del dispositivo) guarda la suscripción y responde `204`; repetir el mismo `endpoint` actualiza la fila (`upsert`), no la duplica. Como el servidor envía a esa URL, el `endpoint` solo se acepta si es HTTPS y de un servicio de push conocido (Chrome/FCM, Safari, Firefox, Edge); cualquier otro host es `400` (evita SSRF). Al ejecutar `PATCH /api/admin/incidents/:id/status` con un estatus distinto del actual, la API envía un push (`{title, body, incident_id, status, url}`, TTL de 24 h) a todas las suscripciones del `reporter_id` de ese reporte **sin esperar** y sin poder fallar el cambio; una suscripción que el servicio de push responde `404` o `410` se borra. Variables: `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY` y `VAPID_SUBJECT` (`mailto:` o URL https), todas juntas o ninguna (sin ellas los dos endpoints responden `503` y no se envía nada). Genera el par con `cd api && npx web-push generate-vapid-keys`; la privada es secreta: solo en `.env` o en el panel de Render (`render.yaml` las declara con `sync: false`). Las pruebas (`api/src/push/`, `api/test/push.e2e-spec.ts`) simulan `web-push`.
- **Seguridad desde el arranque:** TypeORM con `synchronize: false` (el esquema es solo de Liquibase), CORS con allowlist, cabeceras de seguridad (`app.useSecurityHeaders()` de Nest 12.1+: mismos valores que Helmet 8, sin el paquete) y `ValidationPipe` global con `whitelist` y `forbidNonWhitelisted` (400 ante campos inválidos o no declarados). El _rate limiting_ del login lo aplica el módulo `auth` (`@nestjs/throttler`).
- **Módulo nuevo:** copia `api/src/health/` (su comentario en `health.module.ts` explica los pasos: DTOs validados y documentados, servicio, controlador y registro en `AppModule`).
- **Pruebas** (Vitest, sin BD): `cd api && npm ci && npm test`. Las e2e levantan la app con la misma `configureApp` que `main.ts`.

## Despliegue (Vercel + Render)

Solo `prod` despliega; `develop` nunca. Se trabaja en este repositorio (`alexo123456780/AWP-PARCIAL3`) con una rama por ticket → PR a `develop` → PR de _release_ `develop` → `prod`, y cada merge a `prod` que pasa `lint-and-test` despliega solo. El job `deploy-backend` de `.github/workflows/ci.yml` hace, en este orden: **migrar la BD con Liquibase → desplegar la API en Render (deploy hook con el commit exacto) → esperar `/api/health`**. La PWA la construye Vercel por su integración Git al recibir el push a `prod` (rama de producción), en paralelo; es compatible con la versión anterior de la API. Vercel ignora los pushes a cualquier otra rama (`ignoreCommand` de `web/vercel.json`). Mientras la variable `DEPLOY_ENABLED` del repositorio no sea `true`, el job del backend se omite (también sirve para pausarlo).

| Pieza      | Dónde                                                    | Configuración versionada                                                                      |
| ---------- | -------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| API NestJS | Render, servicio web Docker (`civicguard-api`)           | `render.yaml` (última etapa de `api/Dockerfile`, health check `/api/health`, sin auto-deploy) |
| PostgreSQL | Render, base `civicguard-db`                             | `render.yaml`; la API lee `DATABASE_URL` (en local sigue usando `DB_*`)                       |
| PWA        | Vercel, proyecto `civicguard-pwa` (Root Directory `web`) | `web/vercel.json` (fallback SPA; `sw.js` e `index.html` con `no-cache`, `/assets/` inmutable) |

**Configuración única** (las cuentas son tuyas; el repositorio no guarda ningún secreto):

1. **Render:** _New → Blueprint_ con este repositorio (público) y la rama `prod`; crea la API y la BD. Copia de la API su **Deploy Hook** (_Settings_) y su URL pública; de la BD, los datos de **conexión externa** (host, usuario, contraseña y base).
2. **Vercel:** proyecto `civicguard-pwa` (el nombre debe coincidir con `CORS_ORIGINS` de `render.yaml`) conectado a este repositorio, con _Root Directory_ `web`, framework Vite, rama de producción `prod` (la rama por defecto del repositorio) y la variable `VITE_API_URL` (entorno _Production_) con la URL pública de la API. No hace falta ningún token en GitHub.
3. **GitHub** (entorno `production`, restringido a la rama `prod`). Los secretos se piden por prompt, no van en la línea de comandos:

   ```bash
   gh secret set RENDER_DEPLOY_HOOK_URL --env production
   gh secret set DB_JDBC_URL --env production   # jdbc:postgresql://<host-externo>:5432/<base>?sslmode=require
   gh secret set DB_USER --env production
   gh secret set DB_PASSWORD --env production
   gh variable set API_URL --env production --body https://<tu-api>.onrender.com
   gh variable set DEPLOY_ENABLED --body true   # el interruptor va en el repositorio, no en el entorno
   ```

4. Haz un merge a `prod` (o reejecuta el último workflow de `prod`) y comprueba `https://<tu-api>.onrender.com/api/health` y la URL de Vercel.

**Límites conocidos:** el Postgres gratis de Render **expira a los 30 días** (14 más de gracia); la API gratis duerme tras 15 min sin tráfico (arranque en frío de ~1 min); el chequeo de salud del job no distingue la versión nueva de la anterior mientras Render construye; las migraciones corren **antes** de la API, así que cada changeset debe ser compatible con la versión anterior en ejecución.

Guía completa y reutilizable de todo el proceso (decisiones, comandos, verificación y errores reales): [`docs/guia-despliegue-vercel-render.md`](docs/guia-despliegue-vercel-render.md).

## Calidad de código y flujo Git

Requiere Node.js 22.12 o superior. Tras clonar: `npm ci` (instala también los hooks de Husky).

| Comando                | Qué hace                                                      |
| ---------------------- | ------------------------------------------------------------- |
| `npm run lint`         | ESLint sobre todo el repo (`web/`, `api/`, configuración)     |
| `npm run format:check` | Verifica el formato con Prettier (`npm run format` lo aplica) |
| `npm test`             | Pruebas de las reglas de calidad (ESLint y commitlint)        |

- **Sin `localStorage`/`sessionStorage` (RF-5):** ESLint falla ante cualquier uso, incluido `window.`, `globalThis.` o `self.`. Usa IndexedDB (`idb`).
- **Commits convencionales:** `tipo(SCRUM-N): descripción` (por ejemplo `feat(SCRUM-122): agregar CI`). Husky + commitlint rechazan cualquier otro formato.
- **Ramas:** se trabaja en una rama por ticket y se integra con PR a `develop`; `prod` es la rama de producción (equivale a la `main` del PRD) y la única que despliega, y recibe `develop` con un PR de _release_. Los PR hacia `develop` se fusionan solos cuando pasan los checks (`.github/workflows/auto-merge.yml`); el release a `prod` es manual. Ninguna admite push directo: ambas exigen PR y que pasen los checks `lint-and-test` y `liquibase-validate` (sin aprobaciones: el repositorio tiene una sola persona; si se suman colaboradores, súbelas en _Settings → Branches_).
- **CI:** el workflow `.github/workflows/ci.yml` corre lint, formato y pruebas (`lint-and-test`) en cada PR y en cada push a `develop`/`prod`. En cada PR, además, `liquibase-validate` aplica el changelog de la rama base a un Postgres temporal, valida el de la PR (detecta changesets editados por diferencia de checksum) y comprueba que el rollback seguido de update deja el esquema íntegro.
